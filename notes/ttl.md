# Backend 筆記：TTL

## 一句話

TTL（Time To Live）是資料可以存活多久的期限；時間一到，系統就把它視為過期，不再繼續使用。

## 我的理解

TTL 用來限制資料可以存活或維持有效多久，不代表資料一定是最新的。不同資料要依安全性、即時性與重新取得的成本設定不同 TTL。TTL 太短會降低快取命中率並增加資料庫負載；資料更新後若必須立即生效，不能只等待 TTL，還要主動讓舊快取失效。

## 前端類比

它很像瀏覽器快取的 `max-age`，也像 React Query 的 `staleTime`：資料剛取得時可以直接使用，超過指定時間後，就應該重新確認來源是否有更新。

| 前端 | 後端快取 |
|---|---|
| HTTP `Cache-Control: max-age=60` | Redis `EX 60` |
| 查詢結果進入 stale 狀態 | key 過期後讀取不到 |
| 重新向 API 取資料 | 回到資料庫查詢並重建快取 |

差別是 `staleTime` 常表示「資料舊了，可以重新抓」，資料可能仍留在前端記憶體；Redis key 的 TTL 到期後，通常會被當成不存在。

## 實務用途

- **登入驗證碼**：設定 5 分鐘 TTL，因為驗證碼不應永久有效，期限越長，被重複利用的風險越高
- **Session**：讓長時間未使用的登入狀態過期，因為伺服器不能無限保存每一位使用者的 session
- **API 查詢快取**：熱門列表快取 30 秒，因為短時間重複查詢可以省下資料庫成本，而使用者通常能接受些微延遲
- **分散式鎖**：鎖必須有 TTL，因為持有鎖的服務若突然中斷，沒有期限的鎖可能讓其他工作永遠無法繼續
- **暫存任務狀態**：只保留近期匯入或報表進度，因為完成很久的暫存資料沒有持續占用記憶體的必要

TTL 應由資料能容忍多久不更新、資安風險與重建成本共同決定，不是所有 key 都套用同一個數字。

## 常見誤解

- **「TTL 到期的那一毫秒，資料一定立刻從記憶體消失」**：實作可能在讀取時才發現過期，或由背景程序稍後清理；對應用程式而言，重點是到期後不能再讀到有效值
- **「TTL 越短越安全」**：太短會讓大量請求頻繁回到資料庫，降低快取命中率，甚至造成瞬間負載
- **「有 TTL 就不需要 Cache Invalidation」**：TTL 只限制錯誤資料最久存在多久；價格或權限必須立即生效時，寫入後仍要主動讓相關快取失效
- **「每次讀取都延長 TTL 最合理」**：這會變成滑動過期；熱門但已不正確的資料可能一直不消失，必須確認產品真的需要這種語意
- **「所有資料都適合同一個 TTL」**：商品價格、新聞列表與一次性驗證碼的時效要求完全不同，應依使用情境設定

## 10 分鐘動手

建立 `ttl-demo.js`，用可控制的時間模擬一個帶 TTL 的快取：

```javascript
const cache = new Map();
let now = 0;

function setWithTTL(key, value, ttlMs) {
  cache.set(key, {
    value,
    expiresAt: now + ttlMs,
  });
}

function get(key) {
  const entry = cache.get(key);

  if (!entry || now >= entry.expiresAt) {
    cache.delete(key);
    return 'CACHE MISS';
  }

  return entry.value;
}

setWithTTL('homepage', '首頁資料 v1', 5_000);

console.log(get('homepage')); // 首頁資料 v1

now += 4_000;
console.log(get('homepage')); // 首頁資料 v1

now += 1_000;
console.log(get('homepage')); // CACHE MISS
```

執行：

```bash
node ttl-demo.js
```

接著把 `5_000` 改成 `3_000`，觀察第二次讀取也變成 `CACHE MISS`。再思考：如果首頁更新後必須立刻顯示新版，只等待 TTL 是否足夠？答案通常是否定的，還需要主動刪除舊快取。

## 回想題

1. TTL 解決的是「資料可以存活多久」，還是保證資料永遠最新？為什麼？
2. 驗證碼與熱門文章列表的 TTL，為什麼不應只用同一個預設值？
3. TTL 設得太短，可能對資料庫與快取命中率造成什麼影響？
4. 哪些情境需要在 TTL 尚未到期前，就主動讓快取失效？
