# Backend 筆記：SQL vs NoSQL

## 一句話

SQL 用固定結構與關聯來守住資料正確性；NoSQL 用較彈性的資料模型，換取因應不同資料形狀與擴展需求的空間。

## 我的理解

先別把它想成「SQL 比較舊、NoSQL 比較快」。真正問題是：資料之間的關係和規則有多嚴格？

訂單、付款、庫存這類資料通常需要明確欄位、交易與一致性，關聯式資料庫（例如 PostgreSQL、MySQL）很合適。文章、活動紀錄或使用者偏好可能欄位常變、讀取量大，文件型或鍵值型 NoSQL（例如 MongoDB、Redis）會更方便。

NoSQL 不是沒有查詢語言，也不是沒有結構；它只是把結構與一致性的取捨，交給資料庫類型與應用程式一起決定。

## 前端類比

SQL 像 TypeScript 嚴格定義的多張資料表：會員、訂單、商品各自有型別，透過 `id` 關聯；不符合規則的資料盡早擋下。

文件型 NoSQL 像一個可逐步演進的 JSON 物件：不同頁面的設定可以有不同欄位。彈性很高，但前端仍要自己處理欄位缺失、版本差異與資料一致性。

## 實務用途

- 電商結帳：以 SQL 儲存訂單、付款與庫存，讓交易能一起成功或失敗。
- 使用者 session、熱門商品快取：以 Redis 這類鍵值 NoSQL 快速讀寫，並設定過期時間。
- 內容管理或事件紀錄：資料形狀變化多時，可考慮文件型 NoSQL。

同一個系統同時使用 SQL 與 NoSQL 很常見；先從資料需求選擇，不是從流行度選擇。

## 常見誤解

- **NoSQL 比 SQL 快**：速度取決於資料模型、索引、查詢與硬體，不是名稱。
- **NoSQL 不需要設計 schema**：schema 仍然存在，只是可能放在程式、驗證規則或資料慣例裡。
- **SQL 不能水平擴展**：可以，只是策略與成本通常比單純分散鍵值資料更需要規劃。

## 10 分鐘動手

以「使用者收藏文章」為例，先畫兩種資料：

1. SQL：建立 `users`、`articles`、`favorites(user_id, article_id, created_at)` 三張表，思考如何避免同一篇文章被重複收藏。
2. 文件型 NoSQL：寫出一筆 `user` JSON，內含 `favoriteArticleIds` 陣列；再想想收藏數量很大時，整份文件更新會遇到什麼問題。
3. 比較兩種做法：需要查詢「某文章被誰收藏」與「使用者最近收藏」時，哪一種較自然？

## 回想題

1. 若資料需要跨多筆紀錄一起保持正確，你會優先考慮哪一類資料庫？為什麼？
2. 文件型資料庫的彈性，會把哪些驗證責任移到應用程式？
3. 你的前端專案中，哪一份 JSON 設定未來可能適合用文件型資料儲存？
